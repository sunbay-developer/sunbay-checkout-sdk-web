3 · Theming & customization

All three theming layers in one page. Because the fields render in cross-origin iframes (PCI), arbitrary CSS is not allowed — theming goes through a controlled appearance contract: whitelisted design variables, controlled semantic rules, and a colorScheme. Theming can be applied at init (serialized into the iframe src, no flash) or hot-reloaded at runtime via updateCheckout().

A · Global theme (init-time)

Pass appearance.variables + appearance.colorScheme to createCheckout(). These 7 whitelisted variables map to the hosted theme and apply on the first paint.

B · Element rules, express buttons & locale

appearance.rules target controlled semantic anchors (input, input:focus, label, …). Rules can be set instance-wide (via createCheckout) or per Element (via the element's own options.appearance) — the two split fields below each get a different input color to show isolation. The expressCheckout row shows per-wallet buttonType/buttonTheme customization, and the locale buttons switch every mounted Element between English and Chinese via updateCheckout({ locale }).

C · Hot-reload at runtime (updateCheckout)

After mounting, call instance.updateCheckout({ appearance }) to restyle every mounted Element live — no remount, no flash. Toggle the color scheme or push new primary/border-radius variables and watch the card below update in place.

D · Fine-grained customization (single element & express button)

A detail-focused playground. Tune the options below, then either Apply & mount (recreates the Element from scratch) or Hot-update (restyles the live Element with no remount / no flash). For input fields the hot path uses updateCheckout({ appearance: { rules } }) (applied instance-wide by the hosted runtime). The express button's buttonType/buttonTheme/buttonHeight are Element options baked into the iframe, so its Update tries element.update() and falls back to recreating the iframe (the log shows which path was taken). Non-whitelisted values are dropped by the hosted side (PCI-safe).
